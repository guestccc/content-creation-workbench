# 视频字幕提取（VideoCaptioner）设计说明

这份文档说明工作台「字幕提取」功能背后的转写工具 **VideoCaptioner**：
为什么直接调它而不走仓库里的 `vct`、环境检测怎么做、为什么界面上没有
进度百分比、以及判定一条视频成败为什么看产物而不是退出码。

日常使用不必看这里 —— 直接在网页上选视频、点「开始提取」即可，
没装 VideoCaptioner 时页面会给出按平台分好的安装命令。
本文是当你想知道「为什么这么设计」时的参考。

> 实现位置：后端 `backend/app/services/subtitle_env.py`（检测与安装指引）、
> `subtitle_runner.py`（执行器）、`subtitle_job_service.py`（状态机），
> 前端 `frontend/src/pages/SubtitleExtract.tsx`。

---

## 1. 为什么直接调 VideoCaptioner，不走 `vct`

VideoCaptioner 实际装在工具箱目录下（本仓库的**兄弟目录**），仓库里的
`vct`（`vctl/commands/vc.py`）确实包装过一个 `vct transcribe` 命令，
但字幕功能没有复用它，原因有三：

1. **`vct transcribe` 是终端 UI 层**。它用 rich 画表格、打进度给人看，
   后端要的是「起子进程 → 看产物 → 落库」，套一层给人看的 UI 只会碍事。
2. **探测逻辑埋在 `vctl` 包里，且只认仓库内路径**。它的 `VC_ROOT` 指向
   仓库内的固定位置，而 VideoCaptioner 并不装在那儿 —— 照抄过来探测
   必然落空。
3. **我们要的恰恰是「后端自己的检测」**。跨平台候选顺序、结果缓存、
   按平台出安装指引，这些都是接口要直接返回给页面的，理应由后端
   自己掌握，而不是借道一个为终端写的包装。

所以后端直接拼 `videocaptioner transcribe` 的 argv，与 `vct` 互不依赖。

## 2. 环境检测：候选顺序与缓存

检测回答两个问题：装了吗（给出能直接拼 argv 的调用方式）、没装怎么装
（按当前系统给出可复制的命令）。候选按「越确定越靠前」排列，命中即止：

1. `SUBTITLE_VC_PYTHON` 显式指定（用户说了算，先试「解释器 -m」再试「脚本」）；
2. `<VC_ROOT>/.venv/` 下的解释器 —— 官方一键脚本与本机的装法
   （Windows 与 POSIX 的差异只在这一步的目录布局：`Scripts/python.exe`
   对 `bin/python`）；
3. **后端自己的解释器**：`importlib.util.find_spec` 就地判断，命中则
   `sys.executable -m videocaptioner`。这一步**零子进程、零副作用**，
   覆盖「直接 pip install 到后端环境」这一最常见的情况；
4. PATH 上的 `videocaptioner` 脚本，并顺着它找同目录的解释器
   （`-m` 调用比直接调脚本更抗 PATH 与 shebang 差异）。

两个实现要点：

- **探测用 `python -c "小脚本"`，不用 `--version`**。实测 `--version`
  要约 1.2 秒（它会把所有子命令的解析器都建起来），而小脚本只导入包、
  打印版本与配置文件路径的 JSON，约 0.1 秒；
- **结果必须缓存**（默认 30 秒，`SUBTITLE_DETECT_CACHE_SECONDS`）。
  导入 `videocaptioner.cli.config` 会在用户 HOME 下建配置目录 —— 探测
  是有副作用的，不能每个请求都探一次。页面上的「重新检测」按钮走
  `?refresh=1` 绕过缓存（用户刚装完，缓存里的结论已经过期）。

检测**只读不改**：安装命令只是回给前端展示的文本，后端绝不替用户执行
安装 —— 网页进程不该有装软件的权力。

## 3. 为什么没有进度百分比

VideoCaptioner 的进度条（`output.ProgressLine`）**只在 `stderr.isatty()`
为真时渲染**。而后端起子进程时必须把 stdio 重定向到日志文件（持续输出的
子进程接上无人读取的 PIPE，缓冲写满就会永久阻塞），于是输出里没有任何
机器可读的进度。

所以界面只如实显示「第 N/M 条 · 转写中 · 已用 XXs」，不编分母。这与
镜头分割「检测阶段分母未知就不显示百分比」是同一个取舍。每条视频另设
硬超时（默认 1800 秒），卡住的转写会被整组杀掉，不堵死后面的队列。

## 4. 结果以产物为准，不只看退出码

判成功的依据是**「目标 `.srt` 存在且非空」**，退出码只用来填失败原因。
两种边界都来自对 VideoCaptioner 行为的实测：

- **退出码非 0 但字幕已写好**：它可能在收尾阶段（保存、日志）报错，
  而字幕文件其实已落盘。这种情况认成功，但把「命令以退出码 X 结束 +
  日志里的错误行」记到条目上，用户能在详情里看到；
- **退出码 0 但什么都没产出**（比如识别出 0 条语音）：判失败，并从日志
  尾部挑出 `✗ Error:` 开头的行作为给用户看的原因。

相关的命令行细节（读它的 CLI 源码确认，改了就坏）：

- `-o` 必须指向**已存在**的目录且带结尾斜杠 —— 不带扩展名又不是目录时，
  它会把这个值当成**文件名**，字幕就落到一个没有扩展名的文件里去了；
- 一次只吃**一个**文件，批量是后端逐条循环出来的；
- `--asr` 只认 `bijian / jianying / whisper-api / whisper-cpp`，
  `faster-whisper` 文档里提了但代码没实现，传了会被 argparse 拒绝 ——
  所以前端选项里不放它，后端 schema 也直接 422。
