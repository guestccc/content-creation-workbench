# 智能镜头分割（PySceneDetect）设计说明

这份文档说明工作台「智能镜头分割」功能背后的检测引擎 **PySceneDetect**：
为什么选它、命令行上踩过的坑、以及切割为什么默认重新编码。
日常使用不必看这里 —— 直接在工作台网页上选模板、点「开始切分」即可，
本文是当你想知道「为什么这么设计」时的参考。

> 背景：这个功能最早是 `vct scene` 命令行，后来移到了本仓库的网页版
> （前端 `frontend/src/pages/SceneSplit.tsx` + 后端 `backend/app/services/scene_runner.py`，
> 后端最终仍是调用本仓库根目录的 `./vct scene` 完成检测与切割）。
> 本文最初写在原工具箱的 `docs/工具说明.md` 里，随功能一起迁到本仓库。

> Windows 下的启动差异：根目录的 `vct` 是 bash 脚本，Windows 的
> CreateProcess 执行不了无扩展名的脚本（shebang 对它只是文本，硬起报
> WinError 193「%1 不是有效的 Win32 应用程序」）。所以 Windows 上后端绕开
> 脚本、用自己的解释器直接跑模块：`python -u -m vctl scene ...`
> （`vct_launcher()`），同时把工具箱根目录注进子进程的 PYTHONPATH、
> 禁写 .pyc、stdio 强制 UTF-8（`scene_child_env()`）—— 这正是 vct 脚本
> 里那几行 export 的等价物。macOS / Linux 不受影响，照旧直接 exec 脚本。

---

## 1. 为什么需要一个第三方工具

剪映的「智能镜头分割」是**纯视觉**功能：找出画面发生跳变的那一帧，在那里下刀。
`vct scene` 做的事情一样，检测交给 **PySceneDetect**（0.7.1）。

它是**独立安装的 CLI 工具**，不装进 vct 自己的解释器，也不进 VideoCaptioner
的虚拟环境：

```bash
uv tool install scenedetect      # 装到 ~/.local/bin
```

`uv tool install` 会为它建一个隔离环境，装进来的 opencv / numpy 不会污染
任何现有环境，也不会跟 VSR 的 torch 打架。这与 ffmpeg 的处理方式一致 ——
vct 只负责找到它并调用。

## 2. 为什么不用 ffmpeg 自带的 scdet

ffmpeg 有内置的 `scdet` 滤镜，能直接输出每帧的画面变化分数，看起来更省事。
实测下来不用它，有两个原因：

**一是阈值断崖式敏感。** 同一条 90 秒素材：

| `scdet` 阈值 | 检出切点 |
|--------------|----------|
| 5 | 8 个 |
| 10 | 2 个 |
| 15 | 2 个 |
| 20 | 1 个 |

从 5 到 10 直接塌掉，中间没有一个「差不多」的档位。快剪素材本来镜头就碎，
这种灵敏度很难调。

**二是没有最短镜头保护。** `scdet` 只有一个裸阈值，闪光、运镜、画面闪烁都
可能被当成切点，切出一堆几百毫秒的碎片。PySceneDetect 的 `AdaptiveDetector`
对阈值做滚动平均，天然压得住这类误判；`-m/--min-scene-len` 还能把过短的
片段并进相邻镜头。

> 顺带一个坑：ffmpeg 的 `select='gt(scene,X)'` 写法在**本机这个构建上完全
> 不出结果**，一帧都不给。要测就测 `scdet`。

## 3. 命令行上的两个坑

PySceneDetect 的参数语法**不是** `key=value` 那种形式，而是标准 CLI：

```bash
scenedetect -i 视频.mp4 -o 输出目录 -q -m 0.6s detect-adaptive --threshold 3.0 \
    list-scenes --skip-cuts
```

**坑 1：全局选项必须排在检测子命令之前。** `-i` / `-o` / `-q` / `-m` 都是
全局的，写到 `detect-adaptive` 后面会直接报参数错误。

**坑 2：`-m` 的值必须带 `s` 后缀。** 不带会被当成**帧数**：`-m 1` 是 1 帧，
`-m 1s` 才是 1 秒。这个不会报错，只会让结果莫名其妙。

另外 `scenedetect` **没有 `--version`**（会被当成参数错误退出），版本要跑
`scenedetect version` 子命令，从首行 `[PySceneDetect] PySceneDetect 0.7.1`
里取。`vctl/env.py` 的 `probe_scenedetect()` 就是这么做的。

## 4. 输出格式

`list-scenes --skip-cuts` 写出 `<视频名>-Scenes.csv`，标准 RFC 4180 表格：

```
Scene Number,Start Frame,Start Timecode,Start Time (seconds),End Frame,...
```

`vct` 只取序号和起止秒数三列 —— 时间码和帧号 CSV 里也有，但那是给别的工具
用的。注意**视频名里可能带空格或中文**，所以读的时候是按 `*.csv` 找而不是
拼文件名。

## 5. 切割：为什么默认重新编码（重要）

切点是拿到了，但**下刀**这一步有个硬约束：**`-c copy` 的片段起点只能落在
关键帧上**。

实测这批素材的关键帧间隔：

```
0.000  7.033  14.033  21.033  28.033  34.233  39.733  46.133  53.000  59.233 ...
```

**约 7 秒一个关键帧，而平均镜头只有 4 秒。** 后果是灾难性的：

| 片段 | 请求时长 | `-c copy` 实得 |
|------|----------|----------------|
| clip_001 | 1.73s | 1.91s |
| clip_002 | 1.60s | **3.51s** |
| clip_003 | 1.60s | **5.11s** |
| clip_004 | 3.13s | **8.28s** |

scene 2/3/4 的片段全都从**第 0 秒**开始 —— 因为它们的切点前面没有关键帧，
ffmpeg 只能退到开头。29 个片段加起来 **214 秒，原片才 115 秒**。

所以 `vct scene` **默认重新编码**（`-c:v libx264 -crf 18 -preset medium`，
视觉上几乎无损）。加上 `-ss` 放在 `-i` 之前做输入定位，重编码下它依然是
精确的 —— ffmpeg 从关键帧开始解码，然后丢掉目标点之前的帧。

切完实测：**115.44 秒 vs 原片 115.17 秒**，差值来自逐帧取整。

`--copy` 保留下来给关键帧很密的片源（比如每秒都有），那种情况下它又快又无损。

## 6. 检测质量怎么验证的

不能只看着「切出来 29 段」就认为对。这里用了两条独立的交叉验证：

**正向**：用 `scdet=threshold=0` 拿到全片每一帧的画面变化分数，然后检查每个
切点处的分数在全片的**分位**。28 个切点全部落在 **99.1% 以上**（也就是全片
变化最剧烈的 0.9%），而同一镜头内的邻帧分数只有 **0.02–0.32** —— 相差
50～500 倍。**一个误切都没有。**

**反向**：取全片分数最高的 28 帧，其中有 **26 帧（93%）** 正好落在检测出的
切点上。剩下 2 帧是被 `--min-len` 并掉的极短镜头，属于预期行为。

## 7. 性能

| 事项 | 实测 |
|------|------|
| 检测（115 秒 / 3455 帧） | **12.8 秒**（约 285 FPS，含读盘） |
| 切割 29 个片段 | **约 3.5 分钟**（重编码，8 核并行） |

检测比切割快一个数量级，所以**调参数时先用「预览切点」**（工作台上的
预览按钮，对应只检测不切割的模式），反复试到满意再「开始切分」，能省不少时间。

## 8. 多条视频的实时进度

一次勾了十几条视频批量切的时候，用户要能看出**现在切到哪一条、这一条切到
第几个片段了**。所以每条视频都得有自己的进度，而不是一个笼统的「处理中」。

### 8.1 为什么用机器可读的标记

`vct` 每切完一个片段，就往 stdout 打一行：

```
#vct-progress split 3 38
```

契约定义在 `vctl/ui.py`（`PROGRESS_PREFIX` / `PHASE_DETECT` / `PHASE_SPLIT` /
`progress()`），后端 `scene_runner.py` 用 `PROGRESS_MARKER` 正则解析。

**为什么不直接解析人看的那几行？** 那些行的措辞和排版是给终端用户看的，
改一个标点、加一次缩进就可能让解析悄悄失效 —— 而且失效是静默的：进度条不
动了谁也不报错。专门打一行只有机器认的标记，改格式就必须同时改两头的测试。
另外，单镜头视频走的是另一条分支，**根本不会打印进度行**，拿人看的文案当
数据源时连这种正常情况都要额外兜底。

标记必须**行首**匹配：日志正文里出现「#vct-progress」这几个字不算数。

### 8.2 检测阶段不给百分比

| 阶段 | 标记 | 界面 |
|------|------|------|
| 检测中 | `detect 0 1` | 「检测中」+ 转圈，**没有进度条** |
| 切割中 | `split 3 38` | 「切割中 3/38」+ 真进度条 |

检测那一步的分母（整条素材有几个镜头）**得把整条过完才知道**，中途给不出
百分比。标记里的 `1` 是「检测这一步」而不是片段数，后端刻意不把它写进
`current_total_clips`（留 0），前端据此只显示「检测中」——宁可不画，
也不画一根编出来的进度条。

### 8.3 分子取 vct 上报的 done，不是产物文件数

两者大多数时候一样，但**有片段切失败时会分岔**：文件数卡在最后一个数字上
不动，看着像卡死了；而 vct 的 done 照样往前走，用户看到的是「还剩多少」。
这一条的成色（切出来几个、失败几个）由条目自己的 `clip_count` /
`failed_clip_count` 另行如实呈现，两件事分开说。

产物文件数保留为**兜底**：老版本 vct 不发标记时，至少还能靠数文件看出
「这条在往前走」。但一旦读到过标记，就不再退回数文件 —— 日志尾部偶尔被
截断时（`read_log_tail` 按字节截），进度会原地保持而不是来回跳。

### 8.4 落库节奏与「换条清零」

进度字段属于**当前这一条**，所以换视频时必须先清零再起子进程，否则新视频会
顶着上一条的「181/181」开场；任务跑完（含取消）也一律清空 —— 结束后没有
「当前视频」了，接口数据得自洽。

写库有节流（`SCENE_JOB_PROGRESS_SECONDS`，默认 3 秒），避免把 SQLite 敲出
火花。但**第一次不能等**：一条几秒钟就切完的小视频，等满 3 秒才写的话从头到
尾一个进度都刷不出来（真实端到端验证过：8 秒素材整条跑完只用了 0.4 秒）。

### 8.5 实测

一条 240 秒、一条 480 秒的素材同时勾选，前端每 0.1 秒轮询任务详情：

```
index=1 phase=split    11/91      ← 第一条，分母是它自己的 91
index=1 phase=split    57/91
index=2 phase=''        0/0       ← 换第二条：干净起步，不带上一条的残留
index=2 phase=detect    0/0       ← 检测中，没有分母
index=2 phase=split    36/181     ← 第二条的分母 181
index=2 phase=split   172/181
index=2 phase=''        0/0  (success)  ← 结束后清空
```

## 9. 切出来的片段能直接播

片段网格上点封面就播（弹窗里的原生 `<video>`），不必再去文件夹里双击。

### 9.1 为什么必须支持 Range

`GET /api/v1/scene/jobs/{id}/clips/{n}/video` 实现了 HTTP Range
（`206 Partial Content`，见 `backend/app/services/file_range.py`），
这不是「锦上添花的优化」，而是**必须**：

`vct` 切出来的 mp4 **moov 原子在文件尾部**（实测：3054 字节的片段里
`mdat` 在偏移 44、`moov` 在 1632）—— ffmpeg 的默认输出顺序就是这样。
播放器得先拿到尾部的 moov 才知道这个文件有多长、每一帧在哪。没有 Range
的话，浏览器只能把整个文件下完才放；有了 Range，它直接发一个
`Range: bytes=1632-` 把尾部捞走，立刻起播、进度条也能随便拖。

Starlette 的 `FileResponse` 不认 Range（收到也整文件从头发），所以自己写了
一个只做单段、只读文件的 `ranged_file_response`：三种形态
（`0-99` / `100-` / `-100`）都支持，越界或多段返回 `416` 并带上
`Content-Range: bytes */<size>`。

### 9.2 安全模型不变

接口只收「任务 ID + 片段序号」，文件路径完全由任务记录推导 —— 与缩略图
接口同一套 `service.get_clip_path`。**不接收前端传来的路径**，否则这就是
一个任意文件读取漏洞。

### 9.3 顺带一提：要不要给 vct 加 `+faststart`

`-movflags +faststart` 能把 moov 挪到文件头，省掉播放时的第二次请求。
本机播放（localhost）收益可以忽略，而它要多一次 remux，所以**没加**。
哪天片段要传到远端播放，再回来开这个开关。

## 10. 从任务一路点到片段

一次切十几条视频，几百个片段全铺在一个网格里，谁也认不出哪一片是哪条视频
切出来的。所以「查看」改成两级下钻：

```
历史任务 ──查看──> 切片视频任务 #12（这条任务切了哪些视频）
                        └──查看──> x.mp4（这条视频切出的 3 个片段）──点封面──> 播放
```

### 10.1 归属按 item_index 判，不按文件名猜

片段接口（`GET /jobs/{id}/clips`）给每一条都带上了 `item_index`：它归在
哪一条视频名下。原来的响应里只有 `source_name`（视频文件名）和片段文件名，
看着好像能拿名字去归组 —— 但**递归扫描时两条视频同名是常事**
（`甲/口播.mp4` 与 `乙/口播.mp4`），按名字归组会把它们的片段混在一起。
后端本来就是按条目顺序推出来的，顺手带上序号，前面就不用猜。

`index`（全任务连续的片段序号）保持不变 —— 缩略图和播放接口靠它定位文件，
和「归谁」是两件事。

### 10.2 「查看」只开弹窗，不顶掉页面上那条任务

页面上那套「进度卡 + 结果网格」属于**当前这条任务**（刚点「开始切分」的那条）。
翻历史记录是另一回事，把页面顶掉的话，用户回头就找不到自己刚跑的那条了。
所以历史任务的「查看」只开弹窗；弹窗里那条任务如果还在跑，弹窗自己轮询，
清单上的进度是活的。

### 10.3 播放器带着「组」走

播放弹窗里的「上一个 / 下一个」要知道走到哪儿为止，靠的是点开时把**整组
片段**一起交给它：

- 从页面「切分结果」点开 → 组是整个任务的片段，可以一路听下去；
- 从某条视频的片段弹窗里点开 → 组只是那条视频自己的片段，走到头就停在
  原地，**不会串到下一条视频**。

这条边界是真在浏览器里点过的：从 x.mp4 的弹窗里点开，位置显示 `1 / 3`
而不是 `1 / 6`；走到第 3 个时「下一个」自动置灰。

## 11. 勾选前先看一眼：素材列表也能播

「选择素材与输出位置」里列出的每一条视频都带一个「预览」。这个列表是按
**文件名**挑素材的地方，而素材目录里躺着的往往是 `vid_20240913_192834.mp4`
这种名字 —— 光看文件名根本认不出是哪条，选错了就得等一整轮切分跑完才发现。

播放走的是 `GET /fs/preview?path=`（Range，理由见 9.1），而不是 `/fs/list`：
列目录只给元信息，字节流另开一个口子。

### 11.1 为什么落在 `/fs` 而不是本功能

同一个列表在**字幕提取页**上也有一份（`SourceDirCard` 是两个页面共用的），
一键成品的框选步骤还要播用户随手选的任意本地视频 —— 三处的诉求一模一样：
「给个路径，我要播它」。所以后端把原本长在 `/finalcut/preview` 的那段逻辑
搬到 `/fs/preview`，只留一份实现，前端也只剩 `api/filesystem.ts` 里的
`localVideoPreviewUrl`。

### 11.2 白名单与 `/fs/list` 是同一份

`/fs/preview` 用 `scene_job_service.is_video_file` 判后缀 —— 与列目录时
标记 `is_video` 的**同一个函数**。这不是随手复用：两处分开写，就会出现
「列表里列得出来、点开 400」的缝（比如 `.avi` 在场景白名单里、却漏在
预览白名单外）。`tests/test_fs.py::test_preview_covers_every_listed_video`
把这条钉住：`SCENE_INPUT_EXTENSIONS` 里每个后缀都要既能列、又能播。

Content-Type 按后缀查表给（`core/video_files.py` 的 `VIDEO_MEDIA_TYPES`）：
给成 `application/octet-stream` 浏览器会当成附件下载，`<video>` 只会黑屏。
查不到的后缀退回 octet-stream，不会抛 KeyError。

### 11.3 预览按钮不放进 Checkbox 里

列表里每一行是 `<Checkbox>` + `<Button>预览</Button>` 两个独立元素。
按钮要是套进 Checkbox 的 `label`，点预览会连带切换勾选状态 —— 用户只是
想看一眼，不该顺手改了「要切哪几条」。
